Why specs and slicing are central to convergence

Trap 1

The spec starts diverging

Controlled implementation needs details.

More details → more attack surface for inconsistency.

So you refine… and it needs even more refinement.

Spec
new edge case
extra rule
missing behavior
contradiction
another refinement
new dependency
refine → discover → refine again
Docs never ship.
Solution

Divide and conquer

Separate detail by level.

Not every detail belongs at every level.

Only add necessary details.

PRD

intent + control model

why outcome constraints

Plan

gap analysis + sequencing

risks order dependencies

Task

bounded slice + contract

scope contracts acceptance criteria
Convergence improves when each level carries the right amount of detail.
Trap 2

The task becomes entangled

Too many constraints slow convergence.

In such case, the model could fail differently on every pass.

Review can find the gaps, but the task converges slowly and unreliably.

product intent
architecture
edge cases
data model
UX behavior
tests

Entangled task

Pass 1 misses A
Pass 2 breaks B
Pass 3 drifts
An over-entangled task converges slowly and unreliably.
Solution

Measure and slice

A good slice can converge.

A good slice changes one thing.

It has a clear end state.

And it can be checked before implementation starts.

Should you build your own?

Some parts will become products.

But the most valuable parts of a harness are often specific to your codebase, workflow and team.

So you will need to build some of it yourself, anyway.

Productized layer

Generic tools

Reusable infrastructure, models, IDEs, runners and orchestration patterns.

Custom harness layer

Your real advantage

System-specific checks, roles, gates, recovery logic and workflow knowledge.
